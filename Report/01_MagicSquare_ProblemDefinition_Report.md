## STEP 1 — Observation (관찰)

### 질문

1. 현재 우리가 해결하려는 상황은 무엇인가?
2. 왜 4×4 마방진 문제를 다루는가?
3. 이 문제는 어떤 학습 또는 시스템 설계 맥락에서 등장하는가?

### 1. 현재 우리가 해결하려는 상황

**관찰:**  
누군가는 **4×4 격자**에 **1부터 16까지의 정수를 각 칸에 한 번씩** 배치했을 때, **행·열·대각선(또는 그에 준하는 선)**들의 **합이 모두 같아지는 배치**가 존재하는지, 그리고 그런 배치를 **어떻게 찾거나 생성·검증·표현할지**를 다루려는 **미정의 과제** 앞에 서 있다.

더 넓게 보면, 이는 단순히 “정답 하나”가 아니라 다음이 아직 열려 있다.

- **무엇을 “맞다”고 볼 것인가** (행/열만? 대각선? 둘 다? “반마방진” 허용 여부?)
- **입력·출력의 형태** (사용자가 숫자를 넣는지, 프로그램이 자동으로 채우는지, 이미 채워진 격자를 검사만 하는지)
- **누가·언제·어떤 맥락에서** 이 결과를 쓰는지 (학습용 연습, 퍼즐, 시험 과제, 라이브러리 등)

즉, **“4×4 + 합이 같은 배치”라는 수학적 패턴**과 **“그것을 다루는 소프트웨어로 무엇을 할 것인가”** 사이에 **아직 연결되지 않은 간극**이 있는 상황이다.

### 2. 왜 4×4 마방진 문제를 다루는가

| 관찰 가능한 이유 | 설명 |
|------------------|------|
| **규모가 적당함** | 3×3보다 제약이 많고 패턴이 풍부하지만, 5×5보다 탐색·표현·검증이 부담이 적음 |
| **학습 목표에 잘 맞음** | 2차원 배열, 반복문, 합 검증, 조건 분기, (선택) 백트래킹·휴리스틱 등 **프로그래밍 기초**를 한 과제에 묶기 좋음 |
| **“완전한” 마방진의 경계** | 짝수 차원 마방진은 홀수 차원과 **구성 방식이 달라지는** 대표 사례 |
| **검증이 명확함** | 성공/실패를 **숫자 합·중복·범위**로 기계적으로 판별하기 쉬움 |
| **프로젝트 이름** | `MagicSquare_XX`는 **4×4에 초점을 둔 연습·실습** 의도로 읽힘 |

**아직 확정되지 않은 것:** “왜 4×4인가”에 대한 **명시적 목표**(수업 과제, 면접, 게임 퍼즐 등)는 별도 확인 필요.

### 3. 학습·시스템 설계 맥락

**학습 맥락**

- 알고리즘 입문: 제약 만족, 완전 탐색, 규칙 기반 채우기 vs 무작위 시도
- 자료구조: 2차원 격자 표현, 인덱스와 경계
- 품질·검증: 불변 조건을 테스트로 표현하는 연습
- 수학·조합: 짝수 차 마방진을 절차로 옮기는 연습

**시스템 설계 맥락 (축소)**

- 도메인 규칙: “배치가 유효한가?”를 분리된 판별 책임으로 모델링
- 생성기 vs 검증기 분리
- 차원·합·대각선 포함 여부를 정책으로 두는 확장 가능 퍼즐의 축소판

**현재 대화 맥락:** 구현 전 **문제 인식·정의** 단계.

### 관찰 관점 표현 전환

| 피하기 쉬운 말 | 관찰 관점 서술 |
|----------------|----------------|
| “마방진을 만든다” | **16개의 서로 다른 정수를 격자에 배치했을 때, 여러 방향의 합이 동일한지를 탐색·생성·검증하는 과제** |
| “프로그램을 짠다” | **범위가 정해지지 않은 소프트웨어 과제**가 프로젝트명으로 **시작 직전**에 있음 |
| “4×4 마방진 문제” | **짝수 크기 격자 + 선형 합 제약**이라는 **구체적이지만 정의가 열린** 수학·계산 문제 |

## STEP 2 — Why #1

### 질문

왜 마방진을 *완성*해야 하는가?

### 가정한 답 (A)

> **A:** 1부터 16까지를 격자에 한 번씩 배치한 뒤, **행·열·(정의에 따라) 대각선의 합이 모두 같아진 상태**만이 “문제를 푼 것”으로 인정되기 때문이다.  
> 미완성·부분 배치·합이 어긋난 배치는 **정답 여부를 말할 수 없거나**, 과제·프로그램의 **성공 기준이 충족되지 않은 것**으로 취급된다.

### A에서 드러나는 불편함·구조적 문제

#### 1. “완성”의 기준이 하나로 고정되지 않음

- 행·열만 vs 대각선 포함 → **완성의 정의가 갈림**
- **구조적 문제:** “완성”은 **정책(규칙 집합) 선택**이 선행되어야 하나, 결과만 강요되기 쉬움

#### 2. “완성” ≠ “유일한 해”

- 4×4에는 **서로 다른 완성 배치가 다수** 존재
- **구조적 문제:** 이진 성공(완성/미완성) vs **다해(multiple solutions)** 공간

#### 3. “완성”이 생성·검증·표시를 한 덩어리로 묶음

- 검증만 필요한 경우에도 “완성을 만들어야 한다”로 읽히기 쉬움
- **구조적 문제:** 역할(생성 / 검증 / 퍼즐) 혼동

#### 4. 완성은 “쉽게 확인”, “어렵게 달성”

- 검증은 기계적, 생성은 탐색·규칙 필요
- **구조적 문제:** 부분 해·진행 중 상태의 가치가 설계에서 빠지기 쉬움

#### 5. “완성”이 4×4·1~16에 과결합

- **구조적 문제:** 일반 불변식이 아니라 **이번 인스턴스 종착**에 고정되기 쉬움

#### 6. 완성 강박 vs 학습·퍼즐 경험

- 단계적 이해·힌트·부분 점수와 **0/1 완성**이 충돌할 수 있음
- **구조적 문제:** 진단·개선 설계가 생략되기 쉬움

### STEP 2 핵심 모순 (재해석)

> **“완성”은 검증하기 쉬운 이진 목표이지만, 달성은 어렵고, 해가 여러 개이며, “선”의 정의에 따라 의미가 달라지며, 생성·검증·퍼즐이 서로 다른 “완성”을 요구할 수 있다.**

### 후속 확인용 시나리오 (미확정)

1. **완성 =** 자동으로 올바른 배치를 만들어 보여주는 것  
2. **완성 =** 사용자/입력이 조건을 만족하는지 판별하는 것  
3. **완성 =** 빈 칸·일부 칸이 있는 퍼즐을 끝까지 채우는 것

## STEP 3 — Why #2

### 질문

왜 단순 계산이 아니라 **프로그램**으로 구현하는가?

(“단순 계산” = 손으로 격자를 채우고 행·열·대각선 합을 더해 보는 수작업)

### 1. 반복 가능성

- 같은 규칙·절차를 **원하는 횟수만큼** 동일하게 실행
- 여러 해 수집, 정책 변경의 일괄 적용, 시연·실험·회귀 테스트에 유리
- 손계산은 **절차가 시도마다 달라지기** 쉬움

### 2. 검증 자동화

- 완성 조건(합 일치, 1~16 각 1회)을 **매번 전부** 적용
- “거의 맞음”과 “완성”을 **동일 기준**으로 구분
- **생성과 검증 분리**에 유리

### 3. 오류 방지

- 중복·누락·일부 선만 맞춘 채 넘어가기·과신 오류 감소
- 프로그램 버그는 **재현·수정 가능한 실패**로 전환 가능 (손실실수는 기록 없이 사라지기 쉬움)

### 4. 규칙 기반 사고 훈련

- 자연어 규칙 vs 절차 규칙을 **명시적으로 분리**
- 불변 조건, 생성 규칙, 실패 경우를 **이름 붙여** 다루는 연습
- 목적: 속도보다 **사고의 외부화**

### 네 관점 요약

| 관점 | 프로그램이 하는 일 (손계산 대비) |
|------|----------------------------------|
| **반복 가능성** | 같은 절차·정책으로 많은 시도·해·실험을 되풀이 |
| **검증 자동화** | 완성 조건을 매번 빠짐없이, 생성과 분리해 적용 |
| **오류 방지** | 산술·중복·누락·검증 생략을 줄이고 실패를 재현 가능하게 |
| **규칙 기반 사고** | “합 같음”을 검증·생성·실패의 **명시적 규칙**으로 훈련 |

### STEP 3 긴장

- **반복·검증**만 목표 → 검증 중심 범위로도 STEP 3 상당 부분 달성 가능  
- **규칙 기반 사고** 목표 → 생성·부분 상태·테스트까지 범위 확대  
→ “프로그램으로 **무엇까지** 반복·검증·훈련할 것인가”를 고정할 필요 있음

## STEP 4 — Why #3 (핵심 발견)

### 질문

왜 이 문제를 **TDD 방식**으로 설계하려 하는가?

### 1. 무엇이 통제되어야 하는가?

| 통제 대상 | 내용 |
|-----------|------|
| **규칙의 해석** | 어떤 선을 검사하는지, 허용 숫자 집합, 격자 크기 |
| **역할의 경계** | 검증 / 생성 / 표시(출력) 분리 |
| **비결정성·다해** | 출력은 “예시와 동일”이 아니라 **항상 검증 통과** |
| **회귀** | 내부 방식 변경 시에도 **공개된 판별·계약** 유지 |

**핵심:** TDD는 테스트 개수가 아니라 **정의 흔들림·역할 혼동·다해**를 **통제 가능한 계약**으로 고정하는 설계 방식.

### 2. 어떤 불변 조건이 존재하는가?

**완성 상태**

- 4×4, 16칸
- 값 집합 = {1..16}, 각 1회
- 관심 선(행4+열4+대각2) 합 = **34** (4×4·1~16 전제)

**부분 상태 (선택)**

- 이미 쓴 수: 중복 없음, [1,16] 내
- 미배치 표기 일관성

**생성–검증 계약**

- 생성 결과는 항상 검증 통과
- 검증은 같은 입력 → 같은 결과 (재현 가능)

**핵심:** 도메인 불변식이 **측정 가능**하여 TDD에 적합.

### 3. 왜 입력/출력이 명확해야 하는가?

- 테스트가 **명세**가 되려면 Given–When–Then이 성립해야 함
- 실패 **재현** (어떤 격자가 어떤 규칙에서 거부되는지)
- 경계·오류 케이스 **나열** 가능
- 리팩터링 시 **계약만** 유지하면 안전망 역할

**핵심:** 입출력 명확화 = TDD의 **관찰 가능성**; “맞음”을 **예시 동일**이 아닌 **검증 통과**로 정의.

### STEP 4 한 문장

> 마방진은 “완성”이 말로 흔들리지만 합·집합·중복은 기계적으로 통제 가능하며, TDD는 그 통제를 **설계 이전에** 테스트와 명확한 입출력으로 고정한다.

### 설계 전 고정 제안 (3가지)

1. **검증 범위:** 행·열만 / 대각선 포함  
2. **입력 표현:** 4×4 격자 vs 16개 일렬 등  
3. **1순위 책임:** 판별 우선 vs 배치 획득 우선  

(TDD 관점: **판별 + 정·오 격자 사례**부터가 가장 작은 사이클)

## STEP 5 — 진짜 문제 정의

### 1. 표면 문제 정의 (잘못된 정의)

> **“4×4 마방진 프로그램을 만든다.”**

| 한계 | 설명 |
|------|------|
| 목적·이해관계자 부재 | 왜, 누구를 위한지 없음 |
| “마방진” 일원화 | 생성·검증·퍼즐·표시 혼동 |
| 성공 기준 모호 | 행·열 vs 대각선 |
| 솔루션 편향 | 자동 채우기로 읽힘 |
| 학습·품질 목표 부재 | 반복·검증·규칙·TDD 없음 |
| 경계 없음 | 부분 상태·다해·잘못된 입력 미정의 |

**숨은 착각:** 과제 = 격자 출력 vs 실제 = **올바른 배치의 정의·판별·공유**

---

### 2. 개선된 문제 정의 (정확한 정의)

> **4×4 격자에 1부터 16까지의 정수를 각 칸에 정확히 한 번 배치할 때,  
> 사전에 합의한 “관심 선”(행·열·필요 시 대각선)마다 그 합이 동일한지를  
> 일관된 기준으로 판별하고, 필요하면 그 조건을 만족하는 배치를 얻으며,  
> 그 과정과 결과를 반복 가능하고 검증 가능한 형태로 다루는 것을 목표로 한다.**

| 요소 | 내용 |
|------|------|
| **도메인** | 4×4, 1~16, 각 1회 |
| **핵심 질문** | 이 배치가 합의된 규칙을 만족하는가 (필요 시 만족 배치를 얻을 수 있는가) |
| **정책** | 관심 선 범위를 정의의 일부로 고정 |
| **품질** | 동일 입력·규칙 → 동일 판별; 기준 생략 없음 |
| **범위** | 완성·부분 배치 모두 동일 규칙 체계로 다룰 수 있음 |
| **성공** | 예시 동일이 아닌 **규칙 충족** |

**비목표 (이 정의만으로는 말하지 않음):** 유일 격자를 정답으로 두는 것, 수동 계산 완전 대체 그 자체.

### 3. 핵심 Invariant

**정책 가정:** 행·열·두 대각선 모두 검사.

#### 구조·집합

| ID | Invariant |
|----|-----------|
| **I-1** | 격자는 정확히 16칸이다. |
| **I-2** | 사용된 값의 집합은 정확히 {1, 2, …, 16}이다. |
| **I-3** | 각 값은 정확히 한 칸에만 있다. |

#### 합 (마방진)

| ID | Invariant |
|----|-----------|
| **I-4** | 관심 선들의 공통 목표 합(마법합)은 34이다. |
| **I-5** | 네 행 각각의 합은 34이다. |
| **I-6** | 네 열 각각의 합은 34이다. |
| **I-7** | 두 대각선 각각의 합은 34이다. |

#### 판별·과정

| ID | Invariant |
|----|-----------|
| **I-8** | 동일 격자·동일 규칙 → 유효 여부 판단은 항상 같다. |
| **I-9** | 조건을 만족하는 배치를 얻는 결과는 합의된 검사를 통과한다. |
| **I-10** | 규칙 정책 변경 시 유효성 판단이 바뀔 수 있음 — 정책과 불변식은 함께 버전된다. |

#### 부분 상태 (선택)

| ID | Invariant |
|----|-----------|
| **I-11** | 미배치 칸은 일관된 “미배치” 표현을 쓴다. |
| **I-12** | 이미 둔 수들 사이에 중복이 없고 모두 [1, 16] 안에 있다. |

**관계:** I-2·I-3 위반 시 I-5~I-7 논의 무의미; I-5·I-6만으로 I-7 깨질 수 있음.

### 4. 실제로 훈련하려는 사고 능력

| 능력 | 설명 |

## 종합 요약

### 표면 vs 개선

| 구분 | 표면 (잘못됨) | 개선 (정확함) |
|------|----------------|----------------|
| **초점** | 프로그램·출력물 | 규칙·판별·재현 가능한 판단 |
| **성공** | 격자를 만듦 | 합의된 불변 조건 충족 |
| **범위** | 생성만 | 판별 우선, 생성·부분 상태는 선택 |
| **학습** | 미명시 | 규칙·불변식·계약·분리 사고 |

### Why 계층 (STEP 2–4)

| 단계 | 핵심 질문 | 요지 |
|------|-----------|------|
| **Why #1** | 왜 완성해야 하는가? | 완성 = 검증 가능한 종착; 정의·다해·역할 혼동 주의 |
| **Why #2** | 왜 프로그램인가? | 반복·자동 검증·오류 재현·규칙 외부화 |

### 진짜 문제 (한 줄)

4×4에 1~16을 한 번씩 배치할 때, **합의된 선들의 합 일치와 숫자 집합 조건**을 **명확히 정의하고, 일관되게 판별하며, 필요 시 그 조건을 만족하는 배치를 얻는 과정**을 **반복·검증·공유 가능하게** 다루는 것이 과제이며, **규칙·불변식·계약 중심의 사고**를 훈련하는 것이 목적이다.
